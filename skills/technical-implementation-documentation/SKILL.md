# Technical Implementation Documentation

## 核心原则
这是**代码事实文档**，不是理想设计稿。所有实现结论必须对应实际仓库和固定 revision。设计意图、源码明示行为、代码推导和未知项必须明确区分。

## 代码基线
开始前记录：
- 仓库、分支、Commit SHA、工作区是否干净。
- 相关子模块/依赖版本。
- 构建配置和关键 feature flags（仅记录已确认项）。
- 对比上游时，记录准确 upstream revision；否则不要声称是上游差异审计。

## 源码分析流程
1. 从对外入口、配置入口或框架回调定位主路径。
2. 追踪调用方、被调用方和关键虚函数/回调。
3. 识别对象创建、所有权转移、销毁和状态更新。
4. 识别核心数据结构、编码格式、索引和关键不变量。
5. 按真实执行顺序还原正常路径。
6. 单独分析错误、超时、重试、回滚、清理和资源释放路径。
7. 分析线程/进程/协程、锁、队列、异步 I/O 和同步点。
8. 对持久化系统明确区分内存状态、WAL/日志、元数据、数据文件、后台线程和 apply/flush/compaction 等阶段（按项目实际情况）。
9. 对照单元测试、集成测试和运行证据，说明覆盖范围与缺口。
10. 建立“文档结论 -> 文件 -> 类/函数 -> 测试/证据”的追踪索引。

## 推荐章节
1. 模块定位与职责
2. 代码版本与文件结构
3. 核心类和数据结构
4. 初始化与对象生命周期
5. 主调用链
6. 核心执行流程
7. 关键算法/数据格式
8. 并发模型与同步机制
9. 错误处理与恢复
10. 配置、日志、指标和诊断
11. 测试覆盖与已知限制
12. 源码导航索引

## 讲解规范
- 按调用顺序说明“谁在何时调用谁、传入什么、状态怎么变化、返回什么”。
- 关键函数给出仓库相对路径、类名、函数名；行号仅在实际检查对应 revision 后提供。
- 重要变量说明含义、单位、取值范围和更新时机。
- 对复杂路径使用时序图/流程图；对状态变化使用状态表。
- 遇到多分支实现，先说明主流程，再说明会影响正确性的分支。
- 不将接口存在等同于功能已完整实现，不将测试通过等同于全部场景正确。

## 证据等级
- **源码确认**：直接由当前 revision 的代码逻辑支持。
- **测试确认**：由明确测试用例和结果支持。
- **运行确认**：由实际运行日志/指标/报告支持。
- **代码推导**：从代码结构推演但未直接验证。
- **待确认**：当前材料无法支持结论。
禁止把推导、注释或设计文档当作运行事实。

## 交付规则
输出 Markdown；用户需要 DOCX 时使用配套脚本。代码片段应短且解释重点。保留准确文件路径和符号名。不得伪造源码位置、测试结果、性能数据或运行行为。
