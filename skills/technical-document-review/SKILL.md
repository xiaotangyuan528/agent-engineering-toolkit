# Technical Document Review

## 范围
只审查：
- 技术架构设计
- 模块详细设计
- 技术实现文档

不承担 PRD、项目汇报或行政文档审校。

## 审查维度
### 架构设计
- 目标、范围、边界和约束是否明确？
- 架构视图是否覆盖系统上下文、模块、交互和部署（按需）？
- 模块职责与依赖是否清晰？
- 质量属性是否有具体机制支撑？
- 关键决策是否说明备选方案和取舍？
- 故障域、降级、恢复和可观测性是否考虑？

### 模块详细设计
- 接口契约是否完整？
- 核心对象、数据结构和状态机是否闭合？
- 并发模型、锁、队列和同步点是否清楚？
- 资源生命周期和异常路径是否完整？
- 是否可据此开发和设计测试？

### 技术实现文档
- 代码版本是否固定？
- 关键结论是否可定位到文件、类、函数和调用链？
- 设计意图和实际实现是否区分？
- 正常路径、错误路径、并发路径是否与代码一致？
- 测试证据是否真实且没有扩大解释？

### 通用质量
- 术语一致、缩写有定义。
- 图表有标题、图例和正文解释。
- 时序图与文字、源码顺序一致。
- 表格字段含义和单位清楚。
- 没有无证据的性能、安全、可靠性承诺。
- 内容没有重复、跳步或把关键前提藏在附录。

## 缺陷分级
- P0：关键事实错误、架构/实现结论可能导致错误开发或运行。
- P1：关键接口、流程、状态、并发或恢复机制错误/缺失。
- P2：证据、边界、测试、图表或诊断信息不足。
- P3：表达、结构和排版优化。

## 输出
先给总体结论；再输出表格：级别、章节/位置、问题、影响、修改建议、所需证据。区分确认错误、证据不足、设计风险和纯表达建议。不要擅自改写技术语义。
