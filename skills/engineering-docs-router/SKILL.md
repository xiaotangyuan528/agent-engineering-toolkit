# Engineering Docs Router

## 职责边界
本 Skill 只路由以下三类文档：
1. **技术架构设计**：系统边界、架构视图、模块划分、关键技术决策、质量属性和跨模块交互。
2. **模块详细设计**：单个模块/子系统的职责、接口、数据结构、状态、时序、并发、异常和资源生命周期。
3. **技术实现文档**：以实际代码为依据，说明文件、类、函数、调用链、关键算法、状态变化、配置、日志和测试。

不生成 PRD、产品方案、项目计划、领导汇报、营销材料、用户手册或通用行政文档。若用户要求这些内容，明确说明不属于本插件范围。

## 识别逻辑
优先从当前对话、仓库、已有文档和用户附件提取信息，不重复询问已知内容。
- 用户说“整体怎么设计/架构怎么拆/模块怎么协作” -> 技术架构设计。
- 用户说“设计某个模块/接口/类/状态机/并发流程” -> 模块详细设计。
- 用户说“代码怎么实现/调用链/源码分析/实现说明” -> 技术实现文档。
- 一个任务跨多个层次时，先确定主文档，再将其他层次作为章节或关联文档，不重复生成三份相似文档。

## 必要信息检查
确认文档对象、目标读者、文档目的、范围边界、依据（代码/版本/Commit/已有材料）、输出格式和详细程度。能从上下文或仓库确认的不要重复询问。
若关键信息缺失，**一次只问一个最影响正确性的问题**。不要用长问卷阻塞用户。默认中文、Markdown；涉及代码时以仓库实际版本为准。

## 路由
- 技术架构设计 -> `technical-architecture-design`
- 模块详细设计 -> `module-detailed-design`
- 技术实现文档 -> `technical-implementation-documentation`
- 完成后可调用 `technical-document-review` 做质量审查。

## 工作约束
- 设计文档描述目标设计；实现文档描述当前代码事实。必须区分“设计意图”和“当前实现”。
- 不得把推测写成事实。证据不足时标记“待确认”或“设计建议”。
- 不为了套模板而生成无意义章节。
- 先给结论/设计摘要，再给支撑细节；复杂主题采用分层阅读路径。

## 配套资源
仓库根目录 `assets/templates/` 提供技术架构设计、模块详细设计、技术实现和 ADR 模板。根目录 `scripts/render_docx.py` 可将 Markdown 转换为 DOCX。独立安装本 Skill 时，这些仓库级资源不会随单个 Skill 一起安装；需要时从项目仓库获取模板和转换脚本。
