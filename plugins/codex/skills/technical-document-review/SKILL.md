# Technical Document Review

## 审查维度
### 技术实现文档
- 代码版本是否固定？
- 关键结论是否可定位到文件、类、函数和调用链？
- 设计意图和实际实现是否区分？
- 正常路径、错误路径、并发路径是否与代码一致？
- 测试证据是否真实且没有扩大解释？

### 通用质量
- 术语一致、缩写有定义。
- 图表有标题、图例和正文解释。
- 时序图与文字、源码顺序一致。
- 表格字段含义和单位清楚。
- 没有无证据的性能、安全、可靠性承诺。
- 内容没有重复、跳步或把关键前提藏在附录。

## 源码交接稿专项审查

用户明确要求专项审查时，审查当前稿件及其固定 Git 提交。逐项检查以下内容：

- **阅读层次**：开篇交代用途、边界和组件职责；核心场景讲完整请求；同一份文档的详细实现给出关键文件、函数、状态、异常与清理。从场景抽查文内跳转，确认目标存在且有足够说明。
- **图文与源码**：沿一条代表性调用链核对角色、箭头、调用顺序及并发边界。核实关键源码引用的文件、符号与行号，区分静态证据、运行证据与待确认事项。
- **完成与异常语义**：对异步操作分别核对提交、分发、回调和结果获取。按源码核查部分失败、超时、重试、取消及资源清理，标明哪些结果仍未知。

先给总体结论，再按缺陷级别提供位置、影响、源码依据和修改建议。用户要求修订时，直接修改原 Markdown 并复核修订处。仅要求审查时，返回审查意见。审查结论和过程信息放在交付回复中。

## 缺陷分级
- P0：关键事实错误、架构/实现结论可能导致错误开发或运行。
- P1：关键接口、流程、状态、并发或恢复机制错误/缺失。
- P2：证据、边界、测试、图表或诊断信息不足。
- P3：表达、结构和排版优化。

## 输出
先给总体结论；再输出表格：级别、章节/位置、问题、影响、修改建议、所需证据。区分确认错误、证据不足、设计风险和纯表达建议。不要擅自改写技术语义。

## 配套资源
相对于本 SKILL.md 所在目录读取 `assets/templates/` 的适用模板。DOCX 转换使用同目录的 `scripts/render_docx.py` 与 `requirements-docx.txt`。执行脚本时使用该资源的实际绝对路径；输入输出可以位于用户项目中。Mermaid 保留为文本。
